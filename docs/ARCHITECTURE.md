# CookieKeeper — Architecture & Brand

**Status:** Accepted (v1, 2026-07-28) · **Owner:** Yorch · **Scope:** MVP v1.0 + upgrade paths

GDPR/cookie consent management for small EU businesses. One repo, one primary provider, ~€5/month infrastructure, deployable to dev and prd from day one.

## Product Identity

**Name:** CookieKeeper

**Tagline:** Simple GDPR cookie consent for European businesses

**One-liner:** The simplest, most affordable GDPR cookie consent tool for EU small businesses, freelancers, and agencies.

**Category:** GDPR / cookie-consent management (CMP) micro-SaaS

### Positioning

CookieKeeper is the **simplest, most affordable** GDPR cookie consent tool for EU small businesses, freelancers, and agencies. Enterprise CMPs (Cookiebot, Osano, OneTrust) are powerful but overbuilt, expensive (€50–500+/mo), and take training to use. CookieKeeper does the 95% that a small European business actually needs — scan, banner, policy, consent logs, Consent Mode v2 — for €9–29/mo, with an interface you understand in 30 seconds.

**We win on:** simplicity, price, EU data residency, and being genuinely nice to use.
**We do not compete on:** enterprise breadth, custom legal consulting, or a free-forever tier.

### Target Audience

Primary:
- **EU freelancers** running a portfolio or client sites
- **Small agencies** managing consent across a handful of client domains
- **Small e-commerce** (Shopify/WooCommerce shops) that added a tracker and now need consent
- **Indie SaaS founders** who want compliance handled and forgotten

Shared traits: not lawyers, not privacy engineers, time-poor, price-sensitive, allergic to enterprise sales calls. They want to paste one line of code and move on.

### Tone of Voice

**Friendly, direct, human, slightly witty. Anti-corporate. Speak *to* the user, not *at* them.**

Do:
- Short sentences. Plain words. Second person ("you", "your site").
- A little dry humour where it lands — never forced.
- Confident and reassuring about compliance; we remove anxiety, not add jargon.

Don't:

- Fear-mongering about fines as the main hook (mention consequences, don't weaponise them).
- Overpromise. Every claim must be true *today*. "Coming soon" is fine; lying is not.

Three containers per environment (`dashboard`, `api`, `scanner`) plus a `caddy` stack of its own on each app host, and **no `postgres` container anywhere in a deployed stack**. Each environment gets two machines: an application host and a dedicated database host, joined by a private network that only they are on (ADR-24).

That buys three things worth the €15/mo: a dev deploy cannot consume production's CPU or memory, a compromise of the app host — the one that runs a web crawler against arbitrary customer sites — does not put it on the same kernel as the consent-log database, and the database can no longer be the process the OOM killer picks. The workstation compose file still runs Postgres in a container; nobody provisions a second machine to run tests on a laptop.

## 4. Components

### 4.1 Backend — `backend/` (Spring Boot 4 — latest stable, Kotlin, JDK 21, Gradle)

Single modular monolith, one deployable jar, two runtime roles selected by Spring profile:

- **Profile `api`:** REST API — auth, site management, banner config, consent ingestion, policy generation, Stripe webhooks, admin.
- **Profile `scanner`:** No web server; polls the Postgres job queue and runs cookie scans with **Playwright for Java** (official MS library — keeps the scanner in Kotlin, same codebase, no separate Node service). Container built from `mcr.microsoft.com/playwright/java` base.

Package layout (by feature, not by layer):

```
com.complyr
├── auth/          # registration, login, JWT (access 15min + refresh rotation), email verification
├── site/          # domains, snippet generation, verification
├── scan/          # job queue, Playwright crawler, cookie signature DB, classification
├── banner/        # banner config CRUD, versioning, widget-config public endpoint
├── consent/       # consent event ingestion (public), audit log queries, CSV export, retention job
├── policy/        # cookie policy generation (templates × 5 languages), hosted page rendering
├── billing/       # Stripe checkout, customer portal, webhook handler, plan entitlements
├── notify/        # email via Brevo (verification, receipts, scan-complete)
└── common/        # security config, rate limiting, error envelope, i18n bundles
```

Key choices:
- **Auth: Spring Security + JWT, rolled ourselves** (plays to existing strength, zero external dependency, EU story intact). Refresh tokens stored hashed in DB, rotation on use. Password hashing: bcrypt.
- **Public endpoints** (`GET /api/v1/widget-config/{siteKey}`, `POST /api/v1/consent`) are unauthenticated, CORS-open, aggressively rate-limited (Bucket4j in-process + Cloudflare rules), and cacheable (widget-config: `Cache-Control: public, max-age=300` so Cloudflare absorbs the read load).
- **Job queue: Postgres, not Redis.** `jobs` table claimed with `FOR UPDATE SKIP LOCKED`, visibility timeout, max-attempts + dead-letter status. One less service to run; fine for thousands of scans/day.

### 4.2 Dashboard — `dashboard/` (Next.js App Router — latest stable, TS, Tailwind, shadcn/ui)

Customer-facing app: register/login, sites, scan results, banner customizer (live preview embedding the real widget), consent log browser + CSV export, policy preview, billing (Stripe customer portal). Also serves the public marketing/landing pages.

- Deployed as a **standalone-output Node container on the app host** (not Vercel) to keep the single-provider story. Vercel remains a documented escape hatch — nothing in the app assumes local co-location.
- Talks only to the backend REST API. Server state: TanStack Query. No client-side state duplication of server data.
- i18n: `next-intl`, EN/DE/FR/ES/IT.

### 4.3 Widget — `widget/` (vanilla TypeScript, Vite → single IIFE file)

The product's heart and its hardest constraint: **≤20KB gzipped, zero dependencies, async**.

Customer embeds:

```html
<script async src="https://cdn.cookiekeeper.eu/v1.js" data-complyr="pk_live_…"></script>
```

Runtime flow:
1. **Immediately** set Google Consent Mode v2 defaults via `gtag`/`dataLayer` — before config even loads. All **seven** signals are sent on every push, because a signal Google is not told about is assumed *granted*: `ad_storage`, `ad_user_data`, `ad_personalization` (← `marketing`), `analytics_storage` (← `statistics`), `functionality_storage`, `personalization_storage` (← `preferences`) all default to `denied`; `security_storage` is `granted` because it maps to the locked-on `necessary` category. A signal whose category the site's banner does not offer stays denied — the visitor was never asked, so there is no consent to infer. Alongside the defaults the widget sets `ads_data_redaction: true` (lifted only once `marketing` is granted), and, **only** when the embed carries `data-complyr-url-passthrough`, `url_passthrough: true` — that one rewrites the host page's own links to carry the ad-click id forward, so it is the site owner's explicit opt-in, never our default.
1a. **Optionally, region-scoped:** when the embed carries `data-complyr-regions="gdpr"` the defaults push splits in two — an all-`denied` push scoped to `region: [EU 27 + EEA + UK & Crown Dependencies + CH]` first, then an all-`granted` global fallback (Google applies the most specific match, and the scoped push must come first). Google does the geolocation itself, so this costs no round trip and sees no IP. The fallback carries no `wait_for_update`: nothing will ever update it, because the banner is gated on the same regions (step 3) and out-of-scope visitors never see one. Off unless the site owner opts in — granting by default is only defensible if we also stop asking, and asking everyone is always allowed.
2. Fetch per-site config JSON from `cdn.cookiekeeper.eu/cfg/{siteKey}.json` (edge-cached 5 min): colors, position, texts per language, categories, script-blocking rules.
3. If no valid consent cookie → render banner (Shadow DOM, so customer CSS can't break it and ours can't leak). Language auto-detected from `navigator.language`, overridable. Under `data-complyr-regions="gdpr"` the banner is first gated on the visitor's region: the widget awaits the origin-token mint (`GET /api/v1/consent-token/{siteKey}` — already on the banner path, `no-store`, never CDN-cached) which returns a `region` bucket of `"gdpr"`, `"other"` or `null`, classified server-side from Cloudflare's `CF-IPCountry`. Only the **bucket** crosses to the page; the country code never leaves the server and nothing is persisted. The gate fails open — a failed fetch, a timeout, `XX`, or any unrecognised header all yield `null` and the banner shows. An `"other"` visitor gets no banner, no cookie, no consent event and no impression beacon (nothing was asked, so recording a choice would be false audit evidence), but their blocked `text/plain` tags are released so the script-blocking half agrees with the signals half. `Complyr.show()` bypasses the gate entirely — withdrawal must work everywhere.
4. On choice: write first-party cookie `cmplyr` (consent snapshot + config/policy version), update Consent Mode, unblock scripts (`type="text/plain"` + `data-complyr-category` pattern), fire `navigator.sendBeacon` to `POST /api/v1/consent`.
4a. **Consent lifetime.** How long a choice stands before the banner asks again is a per-site banner-config field (`consentLifetimeDays` ∈ {90, 180, 365}, default 365 — CNIL guidance is 6 months, so a customer's DPO can pick it, but shortening it is their call). The widget stamps the deadline **into the cookie at write time** (schema v3: `exp`, matching the cookie's own `Max-Age`) rather than reading it back from config: `init()` enacts a returning visitor's stored consent without fetching config at all, and that property is worth more than retroactivity. Consequences, both deliberate: a config change applies to choices made from then on — a cookie already in a browser keeps the window it was written under until the visitor chooses again; and a v1/v2 cookie with no `exp` is measured against 365 days from its `ts`, exactly the behaviour those visitors already had. The allow-list is closed because the value becomes a `Max-Age` in every visitor's browser; the widget itself only clamps to [1, 400] days (browsers silently cap cookie `Max-Age` at 400) so the backend can add an option without a widget redeploy. Renewal reuses the existing `vid` — the same visitor answering again must not split their audit thread.
4b. **Re-prompt when the site's tracking materially changes (ADR-25).** The same write also stamps `bv` — the site's **consent-basis version** — into the cookie (schema v4). A returning visitor's stored choice is enacted *first* (signals + script unblocking, step 4's fast path), and only then, if the cookie carries a `bv` at all, does the widget fetch config and compare: a strictly higher served version means the site now uses a purpose the visitor was never asked about, so the banner opens again with that config (no second fetch). Enacting first is safe because a category the visitor never saw is simply absent from their decision, and absent is denied everywhere — the new purpose stays blocked for the whole time the check is in flight. Unknown on either side is never stale (a pre-v4 cookie, or a choice made against the widget's built-in fallback config after a failed fetch), so upgrading the widget re-prompts nobody and our own network error cannot re-prompt a site.
5. Expose tiny API: `window.CookieKeeper.show()` (reopen preferences), `.consent()` (read current state) — needed for the legally required "withdraw consent as easily as given".

CI gate: `size-limit` fails the build over 20KB gz. Accessibility: focus trap, ESC, ARIA — reviewed by a11y-architect (consent banners are the most-litigated UI in the EU).

Versioned as `/v1.js` (immutable behavior contract); breaking changes ship as `/v2.js`.

### 4.4 Scanner — inside `backend/`, profile `scanner`

- **Triggers:** site added, manual on-demand re-scan (Pro/Business — enforced by `EntitlementService.requireOnDemandRescan`, Starter sees a locked upgrade prompt), plan-cadence scheduled re-scan (Starter monthly, Pro/Business weekly — `ScheduledRescanJob`, ADR-17).
- **Crawl:** homepage + up to 10 same-origin pages (MVP), Playwright Chromium, before-consent state. Collects: cookies (name, domain, expiry, httpOnly), localStorage keys, third-party request hosts, known tracker signatures.
- **Classify** against a seeded cookie signature DB (bootstrap from the Open Cookie Database, CC-BY) → necessary / preferences / statistics / marketing. Unknowns land in a "needs review" bucket the customer can categorize in the dashboard (their categorizations enrich our signature DB over time — a data moat).
- **SSRF hardening:** verification gates crawl *depth* and *publishing*, **not** whether a domain is crawled at all — an unverified registered site is QUICK-crawled with the same posture as the anonymous funnel (ADR-17), a verified site gets the FULL multi-page depth. `ScanTargetValidator` (fail-closed public-only DNS resolution + off-origin-redirect re-validation) plus container isolation is therefore the **sole** app-layer SSRF guard for **both** authenticated and anonymous crawls; it resolves DNS and rejects private/link-local ranges, no redirects off-origin, hard 60s/page + 10min/job timeouts. Runs in its own container with no inbound ports, behind the **container egress firewall** that denies it every private/link-local/host address at the packet level (ADR-18 — the layer that holds when a DNS rebind beats the validator).
- **Anonymous public-scan path** (`com.complyr.scan`, funnel §12/ADR-12): crawls domains the visitor has **not** verified ownership of, so the ownership check above is deliberately given up and `ScanTargetValidator` (fail-closed, public-only DNS resolution, off-origin-redirect re-validation on **every** hop) is the **sole** app-layer SSRF guard. Compensated by: homepage-only "quick" crawl, `PUBLIC_SCAN` per-IP rate tier, per-IP concurrent-scan cap, 24h per-domain cache/dedupe, and an **off-box container egress firewall (blocking deploy requirement, implemented in ADR-18)**. `claimNextId` orders authenticated scans ahead of public ones so a free-scan flood can't starve paying customers.
- **Post-install blocking verification (ADR-26):** because the crawl is a *before-consent* crawl, it can also check our own work. One `page.evaluate` per crawled page reports whether the Complyr embed is present, whether it carries **this** site's key, and how many `script[type="text/plain"][data-complyr-category]` placeholders the owner has tagged — two booleans and an int, decided in the page so no attacker-influenced string crosses into the JVM (§4). Widget present + a known vendor still firing = that vendor is provably unblocked, and the scan report names it with the exact tag to add. `BlockingVerificationService.verify` is a pure projection of the scan row; the "still unfixed after N days" nudge is a separate site-level streak delivered by `ScanCompletionNotifier` on the existing rescan cadence.
- Scan results feed both the **policy generator** and the **banner's script-blocking suggestions**.

### 4.5 Policy Generator — `policy/`

Template-based (not LLM) cookie policy in 5 languages, filled from scan results + customer business details. Output: hosted page `https://app.cookiekeeper.eu/p/{publicId}` (server-rendered, cached, no auth) + copyable HTML block. Policies are **versioned**; consent events reference the policy version active at consent time (audit requirement).

- **Embeddable cookie table (ADR-27).** The same cookie list, for customers who keep their *own* policy page. `GET /api/v1/public/cookie-table/{siteKey}?lang=` is unauthenticated, rate-limited on the `PUBLIC_POLICY` tier and cached 5 minutes; `CookieTableReadService` resolves every display fallback server-side (provider → domain → `—`, missing expiry → *Session*, unsupported `lang` → default) and orders sections through the same `PolicyContextBuilder.cookies` + `PolicyStrings` path as the generated document, so the embed and the hosted page never disagree. The widget fills any `<div data-complyr-policy>` on the page from a single request, after paint, replacing the element's contents only once it has something better to show — a failed or malformed response leaves whatever the customer had pasted there. Gated on an active site and its public key, deliberately **not** on domain verification (ADR-17) or on a published policy: the customer this exists for may never publish ours.

## 5. Data Model (core)

```
users            id, email, password_hash, locale, created_at, verified_at, deleted_at
                 -- deleted_at non-null = Art. 17 tombstone, holds no personal data (V22, ADR-20)
refresh_tokens   id, user_id, token_hash, expires_at, rotated_from
sites            id, user_id, domain, site_key (public), verified_at, verification_method, plan_limits_snapshot,
                 consent_basis_version, consent_basis_categories, consent_basis_changed_at, consent_basis_added,
                 blocking_alert_since, blocking_alert_notified_at
                 -- verification_method ('snippet'|'dns_txt', V15) paired with verified_at via ck_sites_verification_method_pairs; both cleared on domain change (ADR-17)
                 -- consent_basis_* (V27, ADR-25): what visitors are consenting TO, versioned. NULL categories = never observed
                 --   (a site whose basis was never recorded never re-prompts); '' = observed, nothing decidable in use
                 -- blocking_alert_* (V28, ADR-26): the CURRENT unresolved-blocking streak and when we last
                 --   nudged about it; cleared the moment a scan comes back clean
subscriptions    id, user_id, stripe_customer_id, stripe_sub_id, plan, status, period_end
banner_configs   id, site_id, version, config_jsonb, published_at        -- append new versions
scans            id, site_id, status, started_at, finished_at, pages_crawled, error,
                 widget_detected, widget_site_key_matched, blocked_script_count, observed_trackers
                 -- post-install blocking probe (V28, ADR-26): all four NULL = not measured (pre-probe scan,
                 --   or one that never completed) and the read layer renders *unknown*, never a pass or a fail.
                 --   observed_trackers holds OUR OWN trackers.json keys, never an observed request host (§4)
scan_cookies     id, scan_id, name, domain, expiry, category, provider, is_known
public_scans        id (uuid), domain, status, public_token (opaque read key), email (nullable),
                    ip_hash, error, created_at, updated_at, expires_at   -- acquisition funnel, NOT owned
public_scan_cookies id, public_scan_id (FK → public_scans, ON DELETE CASCADE), name, domain,
                    expiry, category, is_known
cookie_overrides id, site_id, cookie_name, category                     -- customer categorizations
policies         id, site_id, version, language, html, published_at
consent_events   id (UUIDv7), site_id, visitor_id (widget UUID), action, categories_jsonb,
                 banner_version, policy_version, lang, ip_hash, ua_trimmed, created_at
                 -- APPEND-ONLY (DB-enforced). Monthly RANGE partitions from day one.
jobs             id, type, payload_jsonb, status, attempts, locked_until, created_at
```

- `consent_events` is the audit product: no raw IP (SHA-256 with a rotating daily salt — enough for uniqueness/abuse analysis, not re-identifiable), no raw UA, retention default 3 years (`complyr.consent.retention-months`, default 36), deleted only by the scheduled retention job (`ConsentEventPartitionReaper`, ADR-16).
- **Physical shape (V3 migration):** monthly `RANGE (created_at)` partitions with a `DEFAULT` safety-net partition; composite PK `(id, created_at)` (Postgres requires the partition key in every unique constraint); the id is a time-ordered **UUIDv7** (Hibernate `@UuidGenerator` VERSION_7) for sequential B-tree insert locality on the hot write path. `ConsentEventPartitionProvisioner` (a `@Scheduled` + on-startup job) pre-creates the current + `complyr.consent.partition-lookahead-months` (default 3) months so the `DEFAULT` partition stays empty and reclaimable months can be dropped. **This is a hard requirement, not a nicety:** with the V4 append-only trigger in place, any row that lands in `DEFAULT` can be removed only by dropping the whole `DEFAULT` partition (age-blind) — it can neither be aged out by monthly `DROP PARTITION` nor `DELETE`d, so it would breach GDPR storage-limitation (Art. 5(1)(e)). The provisioner therefore also counts `DEFAULT` on every run and logs an error (→ alert) if it is ever non-empty. It leader-guards across replicas via a transaction-scoped advisory lock and creates partitions with transactional DDL.
- **Retention (dropping partitions past the retention window) is `ConsentEventPartitionReaper`** (ADR-16) — the other half of the partition lifecycle. A `@Scheduled` (cron `0 0 4 * * *`, after the three reapers), cron-only (no startup run — destructive DDL must never fire during boot) job that discovers the attached monthly children from the catalog (`pg_inherits`) and drops every partition whose **entire month** is older than `complyr.consent.retention-months` (default 36 = 3 years). The rule is `month < currentMonth − retentionMonths`, so a partition is dropped only once *no* row it could hold is still within retention (over-retains by up to the partition granularity, never under-retains). It **never** touches `consent_events_default` (age-blind — the provisioner's alert owns it) and re-validates each child name against the `consent_events_YYYY_MM` pattern before it reaches `DROP TABLE`. Each drop is its own short transaction under a distinct transaction-scoped advisory lock (leader-guarded across replicas, mirrors the provisioner) with `SET LOCAL lock_timeout`/`statement_timeout` so a `DROP`'s brief `ACCESS EXCLUSIVE` on the parent fails fast rather than head-of-line-blocking the consent-INSERT path. The window is **tenant-blind** (see ADR-16): it is set to the **longest** plan retention (3 yr), so no customer loses evidence they are entitled to; shorter per-plan windows (Starter 12-mo) are a read-layer product limit, not a physical-deletion promise, which is acceptable because the rows carry no re-identifiable PII. `retention-months` is validated `>= 36` (the **longest** plan retention) at startup — a lower value would let a fat-fingered window irreversibly drop evidence a paying customer is still entitled to — and a test guards that floor against drifting below any plan's entitlement. It also logs a WARN if any partition remains past the horizon after a run, so a stuck lock or timeout can't silently stall retention.
- **Account erasure never touches `consent_events`** (ADR-20): "delete my account" deletes everything the account owns and scrubs the `users` row — plus any site that holds consent evidence — to an anonymized tombstone, precisely so the append-only evidence stays referentially valid (`fk_consent_events_site` is ON DELETE RESTRICT) and ages out on the same tenant-blind 3-year schedule as everyone else's. A site with no consent evidence is deleted outright.
- **Append-only is enforced in the database (V4 migration), not just in code:** a `BEFORE UPDATE OR DELETE` row trigger raises on any row mutation. This applies to **every** role including the schema owner the app connects as — chosen over `REVOKE UPDATE, DELETE` precisely because REVOKE is bypassed by the owner and would otherwise force a separate non-owner runtime role + secret. Retention is `DROP PARTITION` (DDL — does not fire row-level DELETE triggers), so time-based deletion still works while individual-row mutation is impossible. Targeted per-row erasure is intentionally unsupported: there is no direct PII (hashed IP, opaque visitor UUID, trimmed UA) and the log is the evidence GDPR Art. 7(1) requires us to be able to produce. The `ConsentEventRepository` also extends the bare Spring Data `Repository` marker (not `JpaRepository`/`CrudRepository`) so no delete/bulk-update method is inherited — the type system reinforces the DB guarantee.
- `public_scans` / `public_scan_cookies` (Flyway V9) are the **anonymous acquisition funnel** — deliberately separate from `scans`: no owner, no history, a **7-day TTL** (`expires_at` set at row creation), an opaque `public_token` as the sole read key, and `ip_hash` (same rotating-daily-salt scheme as `consent_events`, never a raw IP). Unlike `consent_events` this is **replaceable lead data, not audit evidence**, so DELETE is correct: `PublicScanReaper` (§8) purges expired rows and cookies cascade. V10 adds table-level autovacuum tuning to **both** (mirrors V6 for `consent_idempotency`) because the reaper's insert-right/delete-left churn — amplified by per-scan UPDATEs and the up-to-500-row cookie cascade per deleted scan — would otherwise bloat the btrees at Postgres' default 20% dead-tuple threshold.
- Flyway migrations, Testcontainers-backed integration tests, `database-reviewer` on every migration PR.

## 6. Environments & Configuration

There are exactly **two** environments, `dev` and `prd`. The name means the same thing everywhere it appears: a Spring profile, a Compose project, a Terraform workspace, and a directory under `/opt/cookiekeeper/`.

| | dev | prd |
|---|---|---|
| Runs | `cookiekeeper-dev-app`, compose project `cookiekeeper-dev` | `cookiekeeper-prd-app`, compose project `cookiekeeper-prd` |
| Domains | `dev.cookiekeeper.eu`, `api.dev.…`, `cdn.dev.…` | `app.cookiekeeper.eu`, `api.…`, `cdn.…` |
| DB | bare Postgres 16 on `cookiekeeper-dev-db`, private net `10.20.10.0/24` | bare Postgres 16 on `cookiekeeper-prd-db`, private net `10.20.20.0/24` |
| Email | Mailpit container — captured, never delivered | Brevo (EU region), live sender |
| Stripe | test keys | live keys |
| Config | `/opt/cookiekeeper/dev/.env` (hand-edited, `chmod 600`) | `/opt/cookiekeeper/prd/.env` (hand-edited, `chmod 600`) |

**A workstation is not a third environment.** `infra/compose.workstation.yml` runs the same `dev` profile against a repo-root `.env` plus a Mailpit container, with exactly one behavioural override: `COOKIE_SECURE=false`, because a browser silently discards a `Secure` cookie delivered over `http://localhost`. There was previously a `local` Spring profile and an `application-local.yml`; both were removed so that "which environment is this?" has two possible answers instead of three, and so a config path exercised on a laptop is the same one exercised in production.

**Secrets** live only in those `.env` files, plus the database role password set by hand on each database host. Not in git, not in Terraform (every Terraform variable is written to state in plaintext, so a secret passed as a variable is a secret in a bucket — which is why `cloud-init-db.yaml` creates the `cookiekeeper` role *without* a password and the system fails closed until an operator sets one), not in GitHub Actions beyond the credentials the pipelines themselves need (per-environment SSH key, Cloudflare token, state-bucket keys). `deploy.sh` writes only `.env.deploy`, which holds the image tag and nothing else, so automation has no path to overwrite a credential. A secret rotation is: SSH in, edit the file, re-run the deploy — for `DB_PASSWORD`, server first, then the `.env`.

One Caddy instance **per app host** serves that environment's hostnames and terminates TLS with certificates it obtains itself over ACME; `CADDY_ENV` selects `Caddyfile.dev` or `Caddyfile.prd`, both importing a shared `snippets.caddy` so edge policy has one definition. Cloudflare sits in front in **Full (strict)** mode, satisfied by that publicly-trusted certificate. All config differences are environment variables only — images are identical across dev/prd.

**Resource limits.** Every service in both deployed stacks declares `mem_limit`, `memswap_limit`, `cpus`, `cpu_shares` and `pids_limit`, sized for one environment alone on a CX22. The purpose is to choose in advance which container dies under memory pressure rather than letting the kernel's OOM killer pick. Since ADR-24 the database is no longer a candidate at all — it is on a different machine — so the question is only which *application* container yields. The scanner carries the lowest weight and absorbs the pressure; `ScanQueue`'s visibility-timeout lease means a job its worker was holding is reclaimed rather than stranded in `running`. Dev's limits are identical to prd's on purpose: dev is where a too-tight limit is supposed to be discovered, which it cannot do with more headroom than prd.

**Database access is narrow by construction.** Postgres binds only localhost and its private IP; `pg_hba.conf` contains no plain `host` lines, so every network connection must be `hostssl` + `scram-sha-256` from the one app host; ufw admits 5432 from that address alone; and the ADR-18 container egress firewall grants exactly one RETURN through its RFC1918 block, to that database. A Hetzner cloud firewall is deliberately *not* part of this list — it filters public traffic only and cannot see the private network, so treating it as the control would be a false sense of safety.

### 6.1 Infrastructure as code — `infra/terraform/`

Two root modules, deliberately not one:

- **`platform/`** — the four Hetzner servers, the two private networks, the firewalls, the SSH keys, and zone-wide Cloudflare settings (TLS mode, HSTS, minimum TLS version). Shared by both environments and **applied by hand only**. `prevent_destroy` is set on every server, and `user_data` is in `ignore_changes` because cloud-init runs once at creation — editing it must never be a rebuild. The machines are described by a single `servers` map keyed by name, each entry carrying its environment, role, type and static private IP, so adding a host is one map entry rather than a new resource block.
- **`environments/`** — per-environment DNS records, cache rules and rate-limit rules. Applied by the release pipelines, isolated per environment through a Terraform workspace named `dev` or `prd`, with a precondition that refuses to run if the selected workspace and the `-var-file` disagree.

The split exists so that a routine dev deploy's plan can never contain "destroy the production server". State lives in Hetzner Object Storage (EU residency, constraint #2) using Terraform's native S3-compatible locking; Terraform Cloud was rejected because it is a US-hosted processor.

Terraform deliberately does **not** own: secrets, containers (Compose does), the Caddyfile (rsynced by the deploy), or the state bucket itself (chicken-and-egg — created once by hand).

## 7. CI/CD Pipeline (GitHub Actions)

Four workflows, escalating. The gates themselves live in one reusable workflow (`quality.yml`) so "is this code OK" has a single definition and the difference between a feature branch and a release is which inputs are switched on.

```
feature branch / PR  →  validate
  └─ quality(run_tests=false, run_build=false)
       lint + compile + terraform fmt/validate      (paths-filtered)

push to main  →  main
  ├─ quality(run_tests=true, run_build=true)
  └─ build 3 images → GHCR, tagged sha-<sha> + main
     NO DEPLOY. main is always releasable; releasing is a separate decision.

manual dispatch on main  →  release-dev
  ├─ quality(run_tests=true, run_build=true)
  ├─ bump VERSION (+ the two package.json) → commit → tag vX.Y.Z   (bump first, then tag,
  │    so the tag never points at a tree that disagrees about its own version)
  ├─ build images from the TAG → GHCR, tagged vX.Y.Z
  ├─ terraform apply (environments, workspace dev)
  ├─ widget → /srv/cdn/dev/, SSH deploy → dev stack
  └─ smoke: /actuator/health, dashboard, CDN

manual dispatch on tag vX.Y.Z  →  release-prd
  ├─ quality(run_tests=true, run_build=true) on the tagged tree
  ├─ verify the vX.Y.Z images exist in GHCR — refuses to build them
  │    (production must never run an artifact nobody exercised in dev)
  ├─ manual approval (GitHub `production` environment protection rule)
  ├─ terraform apply (environments, workspace prd) — plan printed before apply
  ├─ widget → /srv/cdn/prd/, SSH deploy → prd stack + Flyway migrates on boot
  └─ smoke; roll back by dispatching the workflow on the previous tag
```

`VERSION` at the repo root is the single source of truth for the release number. `backend/build.gradle.kts` reads it (via `-PappVersion` inside the Docker build, whose context is `backend/` and therefore cannot see it); `release-dev` mirrors it into `dashboard/package.json` and `widget/package.json`.

Deploy mechanism: `appleboy/ssh-action` with a deploy-only SSH key, `cd /opt/cookiekeeper/{env} && docker compose pull && docker compose up -d`. No config drift: the compose files live in the repo and are copied as part of deploy.

## 8. Security Posture

- JWT access (15 min) + rotating refresh tokens (hashed at rest); bcrypt passwords; email verification required before adding sites.
- Rate limiting layered: Cloudflare rules (edge) + Bucket4j (app) on auth and public consent endpoints.
- **Consent-origin token** (ADR-13): the public `POST /api/v1/consent` is unauthenticated + CORS-open by necessity, so a captured payload can be replayed with `curl`. An **optional** stateless HMAC token raises that bar: `GET /api/v1/consent-token/{siteKey}` (uncached, `permitAll`, `CONSENT` rate tier) mints `base64url(siteKey\nexpMillis\norigin).base64url(HMAC-SHA256(secret, payload))`; the consent endpoint recomputes the MAC (constant-time), checks expiry (~2 min TTL), `siteKey` == body, and `Origin` == the token's bound origin — **zero DB writes per page load**, fully stateless. The secret is *configured* (not per-process) so a restart/deploy can't invalidate an in-flight token. **Enforcement is evidence-preserving:** absent token → record; present+valid → record; present+invalid/expired/origin-mismatch → `400`. A tokenless event is *never* rejected — an old embedded widget, a privacy browser that strips `Origin`, or a delayed localStorage retry must never lose audit evidence (constraint #3). The widget only attaches a token while comfortably fresh (< 90 s, under the 120 s server TTL) and keeps its retry queue token-free, so a token can never cause a legitimate event to be dropped. *Residual:* replayable within the TTL, and a scripted attacker can still mint-then-forge `Origin` (the mint is unauthenticated) — bounded, not closed, by the per-IP rate tier. It is defence-in-depth, not a cryptographic origin proof.
- Stripe webhooks: signature verification, idempotent event handling, raw event log table.
- Scanner SSRF protections (§4.4); scanner container has no exposed ports.
- **Anonymous free-scan funnel** (ADR-12): abuse control is a **honeypot** field + a `PUBLIC_SCAN` per-IP rate-limit tier + per-IP concurrency cap + 24h per-domain cache — deliberately **no third-party CAPTCHA** (Turnstile/hCaptcha are US processors; EU-residency rules them out). *Residual:* the honeypot is a client-fillable trap, so a bot that leaves it blank isn't stopped by it — it's defense-in-depth with the rate/concurrency caps, not a standalone gate.
- **Public-scan retention:** `PublicScanReaper` — a daily `@Scheduled` job (cron `0 45 3 * * *`, 15 min after the consent reaper) — deletes `public_scans WHERE expires_at < now()` in advisory-lock-guarded batches (`pg_try_advisory_xact_lock`, distinct key from the consent reaper), cookies cascade. This is the mechanism that **enforces GDPR erasure of the lead PII** (domain + email + `ip_hash`) past the 7-day window. Mirrors `ConsentIdempotencyReaper`.
- *Residual PII leak:* the `public_token` travels in the result URL, so it can reach infra access logs / `Referrer` headers. Mitigated by `Referrer-Policy: strict-origin-when-cross-origin` (above) plus not logging full request URLs/query at the Caddy layer. The stored lead `email` must be escaped in any downstream CSV export (formula-injection) / HTML email.
- Headers on dashboard + hosted policy pages: CSP (nonce-based), HSTS, X-Content-Type-Options, Referrer-Policy.
- Postgres runs on its own machine and is not exposed publicly (ADR-24): private-IP `listen_addresses`, `hostssl`-only `pg_hba.conf`, ufw admitting the one app host, and the ADR-18 egress rules granting a single RETURN to it. App-host firewall allows 22/80/443 only, SSH by key; the database hosts allow 22 only and have no `deploy` user.
- Backups: `pg_dump` cron on **each database host** (`infra/scripts/backup.sh`), over the unix socket under `peer` auth so the plaintext dump never crosses a network. Dumps carry visitor PII + append-only consent evidence, so they are **encrypted client-side** with `age` (`pg_dump | gzip | age` — plaintext never touches disk) to a **public** key: the host can *write* backups but cannot *decrypt* them (write-only model; the private identity stays offline). Shipped to Hetzner Object Storage (**EU region** — same provider, no new processor per constraint #2) via rclone with a SHA-256 sidecar, under a per-environment prefix so one host's prune cannot delete the other's copies; rotation ~14-day local / 90-day off-site. `BACKUP_ENV` is derived from `hostname -s` and is fatal if unrecognised — guessing wrong would file production's dump under dev's name. **Restore is drilled** by `infra/scripts/restore-drill.sh` (decrypt → restore into a throwaway scratch DB → sanity-verify → drop `WITH (FORCE)`) as a launch-checklist item and quarterly thereafter.
- `security-reviewer` agent is mandatory on: auth, billing, consent ingestion, scanner, and any endpoint changes.

## 9. Observability

- **Uptime:** two layers (`infra/monitoring/uptime.md`) — (1) BetterStack/UptimeRobot free tier probing api health + dashboard + widget CDN URL from outside (catches box/edge down), and (2) an on-box `uptime-check.sh` dead-man's-switch that asserts app health from inside (health body `"status":"UP"`, not a bare 200) and pings an external heartbeat only when all green, so a dead VPS surfaces as a missing heartbeat. Backend capacity (Tomcat threads + Hikari pool) is CX22-sized in `application.yml` and validated by the `infra/load/` k6 smoke test.
- **Errors:** Sentry free tier — backend (Kotlin SDK) + dashboard. The widget gets **no** Sentry (size + GDPR); widget errors fail silent-safe and are sampled via a tiny beacon to our own API.
- **Logs:** JSON to stdout → `docker logs` + Loki later if needed. No PII in logs (enforced convention + review).
- **Product analytics:** deferred to post-MVP; when added, self-hosted Umami in the same compose stack (GDPR-consistent).

## 11. Scaling Path (documented now, built later)

Ordered by trigger, not by ambition:

The environment split and the database split are already done (ADR-24), so what follows is what happens *inside* that four-machine shape:

1. **Either host saturates:** vertical first — CX32/CX42 on the machine that is actually the bottleneck, which is now answerable because they are separate boxes. A Terraform `server_type` change plus a reboot. Retune `DB_POOL_MAX` and `SERVER_TOMCAT_MAX_THREADS` together; the pool sum across app containers must stay under the database's `max_connections`.
2. **Consent write volume:** `consent_events` is already monthly-partitioned (§5); scaling here is automating partition roll-forward (pg_partman) and, if needed, moving cold partitions to cheaper storage.
3. **Scan queue depth:** scale scanner containers horizontally (SKIP LOCKED queue already supports N workers). If scanning crowds the API, the next step is a third machine running only the `scanner` profile on the same private network — no code change.
4. **Read pressure from analytics:** a streaming replica on a second Postgres host — a configuration change on machines we already own, which is the kind of move ADR-24 made cheap.
5. **DB risk tolerance drops (real revenue):** managed EU Postgres — **priced and deferred, see ADR-29**. Scaleway `fr-par` is the only candidate that survives constraint #2, and it is 700 km from Falkenstein, so the move is only correct as part of relocating the *app* hosts too. The trigger is PITR + failover mattering more than ~€75/mo **and** a willingness to change provider, not just database.
6. **Widget global latency:** config JSON to Cloudflare Workers/KV at the edge (read path already CDN-shaped).
7. Only then: consider extracting the scanner into a separate service. **Nothing in v1 is built as microservices.**

Not on this list: re-merging dev and prd onto one box to save €15/mo. Undoing that is the point of ADR-24.
