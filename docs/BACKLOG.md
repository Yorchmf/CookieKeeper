# CookieKeeper Backlog

Single source of truth for what's left. Replaces the old roadmap/status/track checklists
(consolidated 2026-08-18). Architecture and rationale live in [ARCHITECTURE.md](ARCHITECTURE.md);
how to run the stack lives in [RUNNING.md](RUNNING.md).

Ordering rationale: launch-blockers first, then legal/compliance risk (we are a GDPR product —
the bar is "exemplary"), then revenue/UX usefulness, then accepted-risk cleanup.

Tiers 1–4 are the road to the first production tag. Tiers 5–8 are the "more than an MVP" programme
agreed on 2026-08-20 and are listed **in build order** — within them, item number *is* the sequence.
The ordering principle there is different: the cheapest items whose absence costs the *customer*
money go first, the flagship compliance feature next, then proof and reach, then the index page that
makes all of it findable.

## Tier 5 — Consent correctness (build first)

Cheap to build, and the customer pays for our being wrong. Nothing here is visible on a feature
comparison table, which is precisely why competitors at this price point skip it.

| # | Item | Why it matters |
|---|------|----------------|
| 16 | ☑ **Google Consent Mode v2 depth** | **Done.** `widget/src/consent-mode.ts` now derives all **seven** signals from one place (`signalsFor`) and sends every one of them on both the default and the update push — an omitted signal is assumed *granted* by Google, so completeness is the correctness property. `functionality_storage`/`personalization_storage` map to `preferences`, `security_storage` is granted (locked-on `necessary`), and a category the site's banner does not offer stays denied rather than being inferred. `ads_data_redaction` is on from the first paint and lifts only when `marketing` is granted; `url_passthrough` is opt-in per embed via `data-complyr-url-passthrough`, because it rewrites the host page's own links and is the site owner's call. 7.09 kB gz (gate 20 kB), 13 tests. **`region`-scoped defaults were deliberately NOT built** — see #16a. |
| 16a | ☑ **`region`-scoped Consent Mode defaults + banner geo-targeting** (deferred from #16) | **Done.** Built as the coherent feature the deferral asked for, not a flag on the default push: one embed attribute, `data-complyr-regions="gdpr"`, drives **both** halves, so the two can never disagree. *Signals:* `setConsentDefaults` splits into an all-`denied` push scoped to `region: GDPR_REGIONS` (EU 27 + the outermost regions Cloudflare reports separately + EEA + UK/Crown Dependencies/Gibraltar + CH) followed by an all-`granted` global fallback — scoped first, as Google requires, and no `wait_for_update` on the fallback since nothing will ever update it. *Banner:* the existing `GET /api/v1/consent-token/{siteKey}` mint (already on the banner path, `no-store`, never CDN-cached, no DB work) now also returns `region`: `"gdpr"`, `"other"` or `null`, classified by `GdprRegions.classify` from Cloudflare's `CF-IPCountry`. Only the bucket reaches the page — the country code never leaves the server, nothing is persisted, and a spoofed header only ever costs the sender a banner they could have skipped. *Fallback when geolocation is unavailable:* fails open — failure, timeout, `XX`, `T1`, or a malformed header all yield `null` and the banner shows; only a positive `"other"` suppresses one. *How the consent log records "not shown":* it does not, on purpose — no cookie, no consent event, no impression beacon, because nothing was asked and nothing was chosen; recording a choice would be false audit evidence. Blocked `text/plain` tags are released instead, so script-blocking agrees with the signals. `Complyr.show()` bypasses the gate (withdrawal must work everywhere), and an unrecognised attribute value `warn()`s and falls back to showing everyone. Dashboard: two switches on the site detail page rewrite the snippet live (`withEmbedOptions`), which also finally surfaces `data-complyr-url-passthrough` from #16. 7.62 kB gz (gate 20 kB), 104 widget tests, 294 dashboard tests. |
| 17 | ☑ **Configurable consent lifetime** | **Done.** `consentLifetimeDays` is now a per-site banner-config field — a closed menu of 90/180/365 days (default 365, so nothing changes on deploy) validated in `BannerConfigValidator`, served flat to the widget, and edited from a select in the banner customizer. The design decision worth remembering: the widget **stamps the deadline into the cookie at write time** (schema v3 `exp`, equal to the cookie's own `Max-Age`) instead of reading it from config on load, because `init()` enacts a returning visitor's consent *without* fetching config and that property is worth keeping. Two deliberate consequences: a lowered lifetime applies to choices made from then on (an existing cookie keeps the window it was written under), and a v1/v2 cookie with no `exp` is measured against 365 days from its `ts` — exactly today's behaviour. The widget clamps to [1, 400] days rather than hard-coding the menu (browsers silently cap `Max-Age` at 400), so the backend can add an option without a widget redeploy; renewal reuses the existing `vid` so a visitor's audit history stays one thread. 7.81 kB gz (gate 20 kB), 115 widget tests, 994 backend tests, 299 dashboard tests. |
| 18 | ☑ **Re-prompt when the site's tracking materially changes** (flagship) | **Done** (ADR-25). Consent validity is now versioned by what the site *tracks*, not by what its banner *looks like*: `consent_basis_version` on `sites` (V27) is stamped into the cookie at the moment of choice (schema v4 `bv`) and compared on the next visit. The brief said "stamp the banner-config version" and that was the one thing **not** built — a colour edit would re-prompt a whole site's visitors, which is legally unnecessary, trains customers to fear touching their own banner, and spends the single interruption budget we have on a non-event. Only the scanner may bump it: `ScanConsentBasisListener` fires AFTER_COMMIT on `ScanCompleted` and reduces the crawl through the **existing** `ScanFindings.categoriesInUse` — the same reduction `ScanDiffCalculator` compares, so "what changed" still has exactly one definition. Three rules make it safe on a live customer base: **seed, don't bump** (a first observation is written at the version the site already has, `WHERE consent_basis_categories IS NULL` — deploying re-prompts nobody), **grow, never shrink** (union; a tracker that vanishes and returns is not a second re-prompt for an answered purpose), and **compare against the STORED basis, not the previous scan** (a category can arrive across several scans, or from the signature DB learning what an already-present cookie does). The bump is a compare-and-set, so two scans finishing together bump once. `necessary` is excluded — it cannot be rejected, so it can never invalidate a prior consent. Widget: the stored choice is **enacted before** the check (absent = denied everywhere, so the new purpose stays blocked while it is in flight), the config fetch is paid only by cookies carrying a `bv`, and unknown on either side is never stale — so a pre-v4 cookie, or a choice made against the fallback config after a failed fetch, is never re-prompted by our own network error. Dashboard: `SiteAnalyticsResponse.reprompt` names the change and its categories **scoped to the displayed window** (`changedAt ∈ [from, to)`) — that window is exactly where the impression and interaction-rate denominators step, and the notice says in all 5 locales that the step is ours, not their traffic. 7.95 kB gz (gate 20 kB), 122 widget tests, 1012 backend tests, 303 dashboard tests. |

## Tier 6 — Proof, reach & polish

Turns "we run a banner for you" into "we can show you it is actually working".

| # | Item | Why it matters |
|---|------|----------------|
| 19 | ☑ **Post-install blocking verification** | **Done** (ADR-26). The crawl already had the answer and never said it: it loads every page in its *before-consent* state, so if our snippet is on the page and a known vendor still fires, that vendor is provably not tagged. One `page.evaluate` per page now asks for **two booleans and an int** — embed present (`script[data-complyr]` **or** the `window.Complyr` global, which is the only trace a tag-manager install leaves), embed carrying *this* site's key, and how many `text/plain` placeholders were already tagged — merged across pages onto four nullable `scans` columns (V28). The site-key comparison happens **in the browser** against the key we pass in, and matched vendors are stored as keys of our own `trackers.json`: nothing observed on an attacker-influenced page is persisted or logged (§4). All-NULL means *unknown*, rendered as neither a pass nor a fail, so historical scans show no card at all rather than a fabricated verdict. The dashboard panel names each vendor and prints the literal line to write — `<script type="text/plain" data-complyr-category="statistics" data-src="…">` — with the attribute names deliberately **outside** the message catalogue (a translated attribute is a broken install) while every word around them is localized in all 5 locales. `blockedScriptCount` is what turns a bare accusation into "you tagged 3 scripts and missed this one". The nudge rides the **existing** rescan schedule rather than a new job, and fires on exactly the path that would otherwise stay quiet — the unchanged scheduled scan — because a site that has been failing for a fortnight is what "nothing changed" hides. Two design points worth keeping: the verdict is a **pure projection of one scan row** (no site state, so an old report can never claim today's problem) while the streak lives on `sites` (7-day grace, 14-day repeat); and **recording** the streak runs for every completed scan including MANUAL — so a hand-triggered re-scan that fixes it clears the clock — while **claiming** a nudge is a separate compare-and-set done only where the mail actually goes out, so a declined send can never burn one. `NOT_INSTALLED` is never nudged: onboarding owns "install the snippet", and this exists for the customer who did. 1031 backend tests, 309 dashboard tests. |
| 20 | ☑ **Embeddable cookie table** | **Done** (ADR-27). `<div data-complyr-policy></div>` anywhere on the customer's own policy page is now filled by the widget from `GET /api/v1/public/cookie-table/{siteKey}` — addressed by the **public key already in their embed snippet**, so there is no new identifier and nothing to configure. Everything that could be a decision lives on the server: `CookieTableReadService` goes through the *same* `PolicyContextBuilder.cookies` + `PolicyStrings` path as the generated document, so section order, empty-category skipping, the provider→domain→`—` and missing-expiry→*Session* fallbacks and the wording cannot drift between the embed and `/p/{publicId}`. The widget's half is small and defensive: **one** request no matter how many markers are on the page, mounted after `DOMContentLoaded` with a 4 s timeout so it never blocks host render, built entirely from `createElement`/`textContent` (the widget still has **zero** HTML sinks — the endpoint deliberately returns data, not HTML), and it replaces the element's contents **only on success**, so a failed fetch or a malformed payload leaves the customer's own pasted table standing. Language comes from `data-complyr-policy="de"`, else the page's `<html lang>`, else the browser — and an unsupported code falls back to the default instead of 400ing, because a stray `lang` attribute on someone else's page must never cost them their cookie table. The one asymmetry worth remembering: the gate is the **widget-config** gate (active site, public key), **not** the hosted page's domain verification (ADR-17) and not a published policy — we gate `/p/{publicId}` because *we* publish a claim about a domain we don't control, whereas here their own server publishes it, and requiring either would break the feature precisely for the lawyer-approved-page customer it exists for. Dashboard: a *Live cookie table* card on the policy page, shown whether or not a policy has been generated, mirroring that gate. 8.89 kB gz (gate 20 kB), 133 widget tests, 1043 backend tests, 309 dashboard tests. |
| 21 | ☑ **Banner accessibility — WCAG 2.2 AA + EAA conformance** | **Done** (ADR-28, statement in [ACCESSIBILITY.md](ACCESSIBILITY.md)). The audit found one real defect and a set of smaller gaps. The defect: the preferences dialog's focus trap compared the active element against `first`, but initial focus sits on the **non-tabbable dialog container**, which indexes as `-1` — so the very first Shift+Tab a visitor pressed walked out of the shadow root into a page we had just made `inert`, with nothing to land on and no obvious way back (2.1.2). Fixed, and both wrap directions are now regression-tested. The rest: `lang` on both dialogs, set to the language **actually rendered** — resolution moved into one `config.resolveLanguage` shared by the texts, the `lang` attribute and the consent event, so the audit record now says what the visitor *read* rather than what their browser *preferred* (3.1.2); 24 px targets on the category labels and the attribution link via `line-height` rather than font-size (2.5.8); the always-active badge's text repainted in `textColor` so the looser 3:1 pair can never leak into body copy; `prefers-reduced-motion` broadened to every transition and animation. The structural change is **contrast enforced at the API**: `textColor`/`background` ≥ 4.5:1 (1.4.3) and `primaryColor`/`background` ≥ 3:1 (1.4.11 — a button fill is a UI component, not text; the text bar would ban ordinary brand colours for nothing), through a single `ColorContrast` shared with `WidgetConfigMapper` so "readable" has one definition. The derived button *label* is deliberately unchecked — best-of-black-or-white provably clears 4.5:1 against **every** background, now pinned by a sweeping test instead of a comment. The customizer shows the live ratio beside each picker and holds Save, so nobody meets this rule as a 400. The one thing we chose **not** to fix: the banner is still not a focus trap and not `aria-modal` — holding an entire site hostage behind a cookie notice is a worse barrier than the overlap it would fix, and it is recorded as a known limitation rather than quietly omitted. +0.39 kB gz (8.89 → **9.28 kB**, gate 20 kB), 145 widget tests, 1053 backend tests, 314 dashboard tests. |

## Tier 7 — Make all of it findable

| # | Item | Why it matters |
|---|------|----------------|
| 22 | ☑ **In-app feature index — one page listing everything the product does** | **Done.** `/features`, last in the sidebar, listing all 22 capabilities in the order a customer walks them: get installed → tune the banner → publish the policy → prove it worked → run the account. The whole page is driven by one pure table, `lib/features/catalog.ts`, so adding a capability is a row plus its two strings; its inclusion rule is deliberately **a place you can go and use it**, which is why `priorityScan`, the site cap and the retention window are *not* cards — they are the plan comparison on `/billing`, and an "Open" button that opens nothing would be a lie. Gated features are **listed, not hidden**: `useEntitlementGate` is reused verbatim, so locked renders the same `LockedFeature` affordance with its upgrade path, and a *failed* entitlement fetch shows a retry instead of telling a paying customer to upgrade. The hook is called from a separate `GatedCard` component rather than inside the `.map`, so the rules of hooks survive the catalogue changing shape. Two things the build could not catch and tests now do: **every destination is asserted against a real `page.tsx`** — the first draft pointed three cards at `/sites/{id}/scans`, which compiles and 404s, because scan history lives on the site page itself — and every catalogue key is asserted to have a title and description in all five locales, since a missing key is a blank card in production. Per-site features deep-link only when the account has exactly **one active site** (the ordinary case) and otherwise fall back to `/sites` with an explicit hint, so the fallback never reads as a broken link. The "Open" control is a `Link` wearing `buttonVariants`, not `<Button render={<Link/>}>`, because Base UI would put `role="button"` on an anchor that navigates; its visible label stays "Open" while `aria-label` names the feature, which satisfies 2.5.3 and keeps a screen-reader link list meaningful instead of twenty-two identical entries. 329 dashboard tests. |
